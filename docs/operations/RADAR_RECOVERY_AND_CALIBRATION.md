# 레이더 정지 복귀와 PI 주행 실험

## 현재 레이더 동작

Pi 발행자는 UART 레이더 프레임에서 `x/y/z/velocity`를 읽고 점별 반경 거리로 변환한다. PC로 보내는 요약에는 가장 가까운 점의 `min_distance_m`, 위험점 수, 상태와 발행 순번이 들어 있다. 현재 코드에서는 0.15~0.40m 범위에 점이 3개 이상인 프레임이 두 번 이어지면 `EVADE`, 해당 범위의 점이 없는 프레임이 두 번 이어지면 `CLEAR`다. 이 값은 현행 검출 정책이며 실제 제동거리나 모든 방향의 주행 가능 거리를 의미하지 않는다.

PC는 `EVADE`, `UNKNOWN`, 통신 오류 등을 이동 차단으로 고정한다. 정상 `CLEAR`가 돌아와도 Qt의 **레이더 해제 확인 · 새 이동 허용**과 ESP32의 새 STOP 응답이 필요하다. 차단 전에 실행한 명령이나 승인 토큰은 재사용할 수 없다. [레이더 운영 가이드](../RADAR_OPERATION_GUIDE.md) · [관제 연동](../RADAR_LLM_INTEGRATION.md)

## 제안하는 적용 순서

1. **레이더 정지 후 자동 준비.** 처음에는 재생 로그와 모의 장치에서만 검증한다. 일반 장애물 감지에 한해 같은 레이더 부팅에서 정상 `CLEAR`인 서로 다른 센서 프레임이 일정 기간 연속으로 도착하고, 차단 이후 발급한 STOP의 ESP32 응답이 확인되고, 이전 실행 세션이 종료된 경우에만 새 명령을 받을 수 있는 상태로 전환한다. Pi의 주기적 UDP 재전송 순번을 새 센서 프레임으로 세지 않도록 센서 프레임 번호와 데이터 나이를 함께 수신한다. 비상 정지, 센서·통신 끊김, 장치 재부팅, 제어권 변경, 운영자 감시 종료는 수동 복구가 필요하다.
2. **방향별 장애물 정보.** 현재 안전 패킷을 유지한 채 (x, y, z)와 센서 프레임 번호를 관측 전용으로 기록한다. 센서 장착 위치와 방향을 차량 좌표로 보정하고, 정지 물체·사람·작은 물체에서 전방/측면/후방의 검출 범위와 사각지대를 측정한다. 한 개의 최단 거리로는 회피 방향을 고를 수 없다. 측면 횡이동을 할 때는 이동 방향의 센서 시야와 로봇 몸체 전체가 지나갈 공간을 확인해야 한다. 반사가 없다는 이유만으로 미관측 방향을 통과 가능으로 처리하지 않는다. [TI mmWave SDK 포인트 클라우드](https://dr-download.ti.com/software-development/software-development-kit-sdk/MD-PIrUeCYr3X/03.04.00.03/mmwave_sdk_user_guide.pdf)
3. **회피 경로 제안과 실행.** 검증된 공간이 확보되면 관제에서 원 목표와 마지막 확인 위치를 기준으로 짧은 회피 구간을 만든다. 시뮬레이션에서 먼저 2D로 제안하고, 물리 적용은 자동 주행을 사전 승인한 모드에 한정한다. 기존 패킷 차단 경로에서 모든 구간을 계속 검사하며, 구간 사이에 새 STOP을 확인한다. 장애물이 이동하거나 센서가 가려지거나 남은 위치를 신뢰할 수 없으면 대기한다. 종료된 명령을 그대로 재전송하는 대신 그 시점의 위치와 관측으로 다음 구간의 이동량을 다시 계산한다. 손동작·수동 제어는 새 사용자 입력이 필요하다. [Nav2 Collision Monitor 설계](https://docs.nav2.org/jazzy/configuration_and_development/configuration_guide/core_servers/collision_monitor/)

전역 `EVADE`가 계속되는 동안에는 제안된 회피도 대기한다. 첫 회피 구현은 정지 구역 바깥에서 장애물을 일찍 발견해 감속하고, 사전에 확인된 방향으로 경로를 바꾸는 방식이 적합하다. 전방 장애물이 남아 있어도 정지 후 측면으로 이동하려면 방향별 안전 판단과 차체가 지나갈 전체 공간의 관측이 필요하다. 이는 현재 전역 차단 정책을 변경하는 별도 단계다.

거리 기준은 주행 속도별로 **감지부터 STOP 전달까지 이동한 거리 + 실제 제동거리 + 측정 오차 및 여유 거리**를 실측한 뒤 정한다. 정지 진입과 해제에는 별도 기준을 둔다. 최초 검증에서는 한 프레임만 CLEAR인 경우, UDP 중복·누락, 장애물 재등장, 측면 미관측, 정지 응답 누락, 긴급 정지, 안전 센서 재부팅에서 새 모션이 생성되지 않는지 확인한다.

## 현재 제공하는 거리 실험 도구

SIMPLE V2의 바퀴 속도 제어는 피드포워드와 PI를 사용한다. 현재 코드 상수는 `WHEEL_PI_KP=1.3`, `WHEEL_PI_KI=1.5`이며 D항은 없다. 이 상수는 펌웨어에 포함된다. 실험 도구에서 프로필 값을 기록하면 빌드별·조건별 실측을 비교할 수 있다.

```powershell
.\.venv\Scripts\python.exe scripts\compare_distance_trials.py docs\operations\distance_trials.example.json
```

1. [예제 양식](distance_trials.example.json)을 로컬 `logs/` 아래에 복사한다. 합성 자료에서 확인한 뒤, 실제로 잰 자료에는 `evidence`를 `OPERATOR_MEASURED`로 지정한다. 한 파일에는 바닥, 전원 상태, 하중, 타이어, 속도와 펌웨어 기준을 같은 조건으로 유지한 실험만 기록한다. 프로필 이름에 사용한 빌드를 식별할 수 있는 정보를 붙인다.
2. 기존 [바퀴 시험](../MOTOR_TEST_GUIDE.md)에서 방향과 속도 응답을 검증한 뒤, 현장 승인과 [기존 시험 절차](../C6_HARDWARE_PREFLIGHT.md)에 따라 통제된 바닥에서 기존 Qt 이동 실행의 단일 직선 블록을 시험한다. 각 조건에서 같은 방향과 길이를 반복하고 한 번에 조정 변수를 하나만 바꾼다.
3. 새 STOP을 확인한 뒤 줄자 또는 보정한 상부 카메라에서 이동 방향으로의 차체 변위를 재고 `measured_cm`에 입력한다. 요청 반대 방향은 음수로 기록한다. 선택 필드 `log`에 해당 Qt 자연어 실행 JSONL 경로를 넣으면 도구가 동일한 단일 동작, 목표 도달, 그 뒤의 STOP, 완료를 확인한다. 경로는 양식 파일에 상대적이거나 절대 경로다.
4. 출력에서 목표 대비 실측 편차, 평균 절대 오차, 반복 간 표준편차, 기준 프로필과의 차이를 확인한다. 로그를 연결하면 목표 도달 시 엔코더 추정 거리와 실측의 차이, 유효 샘플이 있는 바퀴의 속도 추종 오차도 표시한다. 속도 추종이 개선돼도 바닥 실측 차이가 남으면 차륜 지름, 미끄럼, 축 방향, 제동 거리와 측정 방법부터 따로 확인한다.

실험 도구는 파일을 읽어 비교 JSON을 출력한다. 실시간 이득 적용은 별도 벤치용 인터페이스가 필요한 후속 단계다. 후보 이득의 상하한, 바퀴 띄움, 새 STOP 확인, 적용 후 복원 절차가 준비되면 별도 구현을 검토한다. 본 도구의 예제와 테스트에는 합성 데이터를 사용했다.

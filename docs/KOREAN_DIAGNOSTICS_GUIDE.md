# 한국어 대시보드와 ESP32 연결 진단

현재 사용 안내다. 이전 검증 문서의 47개·64개 결과와 영어 화면 명칭은 과거 단계의 기록이다. 기본값은 시뮬레이션이며 실제 장치의 자동 추종·손동작 출력은 차단된다.

## 실행

프로젝트 폴더에서 `run_simulation.bat`를 실행하거나 다음 명령을 사용한다.

```powershell
.\.venv\Scripts\python.exe -m python_controller --ui dashboard
```

카메라 없는 합성 화면 확인은 `--dashboard-preview`를 추가한다. 합성 화면은 실제 장치 연결을 허용하지 않는다. 직접 모듈만 실행하면 이전 OpenCV 화면이 열리므로 `--ui dashboard`를 명시한다.

탭은 **종합 현황 / 영상 인식 / 이동 및 모터 / 시험 및 기록 / 모터 동작 시험**이다. 화면·버튼·상태·손동작·안전 사유·경고창은 한국어이며, 괄호 안 진단 코드와 JSON 필드는 원문을 유지한다. 영상 인식 탭은 한국어 안내가 있는 원문 기록이다. 손동작은 손바닥 펼침·주먹·엄지 올림·엄지 내림으로 표시한다.

## 모터를 움직이지 않는 연결 진단

1. ESP32 시리얼 모니터를 115200bps로 열어 `STATUS`를 확인한다. 현재 `IP`, `MODE`, `fault`, `UDP rx/accepted/rejected`, `session`, `seq`, 모터별 수치를 확인한다. USB 연결 자체는 Wi-Fi 연결을 증명하지 않는다.
2. 기존 펌웨어는 `WiFi.begin()`을 사용하고 소스에 고정 IP 설정이 없어 DHCP 주소를 사용한다. 과거 `10.182.7.50`·`10.232.69.103`을 현재 주소로 가정하지 않는다.
3. **모터 동작 시험**에서 현재 주소를 입력하고 **IP 저장**을 누른다. `settings/connection.json`에 주소만 저장하며 연결하지 않는다.
4. **네트워크·수신 포트 점검**으로 선택된 노트북 IP·인터페이스·직접 연결 대역·ICMP 응답·UDP 8889 점유·방화벽 프로필을 확인한다. 이 버튼은 UDP 명령을 보내지 않는다. 일시적 포트 바인딩 검사와 ICMP 1회만 수행하며 백그라운드에서 실행한다. 네트워크가 바뀌면 다시 점검한다.
5. 노트북과 보드를 통신 가능한 네트워크에 연결한다. 다른 대역이면 경로를 확인한다. ICMP 무응답만으로 UDP 차단을 확정하지 않는다. 핫스팟·공유기의 단말 격리와 Windows 방화벽의 해당 Python 실행 파일에 대한 수신 UDP 8889 규칙을 확인한다. 방화벽을 통째로 끄는 방식은 사용하지 않는다. 프로필의 활성화 여부만으로 실제 차단 여부를 알 수 없다.
6. **UDP 통신 연결만 승인합니다**를 선택하고 **UDP 연결**을 누른다. PC는 수신 `0.0.0.0:8889`를 준비하고 ESP32의 `현재 IP:8888`로 새 세션의 STOP을 보낸다. 텔레메트리 송신자는 `ESP32 IP:8888`, 목적지는 노트북 `:8889`여야 한다. 접속만으로 `cmd_vel`을 보내지 않는다.
7. 연결 진단의 여섯 단계를 확인한다. 숫자 IP 형식 정상과 실제 ESP32 주소 확인은 별개다. 수신 대기 준비·실제 패킷 도착·세션과 seq·유효 NETWORK 상태·모터 준비를 각각 표시한다. 최신 정지 응답을 얻은 뒤에만 무구동 heartbeat를 사용한다. **정지 상태 생존 통신 확인**으로 재확인할 수 있다.
8. `MANUAL_TEST`가 관측되면 바퀴를 공중 고정한 상태에서 시리얼 `STOP` → `AUTO` → `STATUS`로 네트워크 모드를 확인한다. `AUTO`는 네트워크 제어 모드 선택이며 사람 자동 추종 실행 명령이 아니다. 호스트에서 거절된 응답도 원문의 mode·fault·session·seq를 확인할 수 있다.

연결 실패는 세션 JSONL에도 남는다. 수신 전에는 미검증, 수신 대기 중에는 확인 중으로 표시한다. 별도 ACK 패킷은 없으며 UDP 송신 성공을 명령 실행 성공으로 표시하지 않는다. 오류가 남으면 원인을 먼저 확인하고, fault를 자동 해제하거나 다시 구동하지 않는다.

## 한 방향 수동 시험

1. 통신·최신 정지 응답·fault 없음·세 모터 목표/측정/PWM/엔코더 수신을 먼저 확인한다.
2. 세 바퀴를 바닥에서 띄우고 플랫폼을 고정한다. 모터 전원과 물리 전원 차단 수단을 확인한다. 화면의 전압·STBY·공통 GND·배선 점검은 사용자 관찰 기록이며 자동 실측 결과가 아니다.
3. 화면을 아래로 내려 공중 고정·전원·차단 수단 확인과 **짧은 모터 시험 한 번을 승인합니다**를 선택한다. **모터 시험 1회 활성화** 후 원하는 방향 버튼 하나를 누른다.
4. 기본 저속은 선속도 2.5cm/s, 각속도 0.2rad/s, 0.8초, 약 10Hz다. 펌웨어 SLOW 상한 5cm/s·0.5rad/s, 이동 워치독 300ms를 유지한다. 초기 설정이나 PWM을 자동으로 높이지 않는다.
5. 시험 종료·통신 지연·fault·화면 갱신 중단·긴급 정지 시 이동 명령을 차단하고 STOP을 시도한다. 이전 이동을 heartbeat로 유지하지 않는다. 다음 시험에는 새 정지 응답과 명시적 재승인이 필요하다. 여러 방향 자동 연속 시험은 없다.
6. 전진·후진·좌우 이동·좌우 회전을 각각 따로 시험한다. 원래 운동학상 전진에서 M1 목표가 0일 수 있으므로 전진 한 번만으로 세 모터 고장을 판단하지 않는다.
7. 모터별 실제 회전과 엔코더 부호를 관찰한 뒤 완료 시험을 선택해 메모와 **육안 관찰 저장**을 기록한다. 엔코더 부호 일치와 실제 회전 방향·본체 주행은 별도 검증이다.

정지 버튼이나 상단 **긴급 정지 [Space]**를 사용할 수 있다. 프로그램 종료 시 STOP을 시도하며 실제 PC/프로세스 장애 시에는 ESP32 워치독이 별도로 남는다. 실제 보드에서 정지와 전원 차단을 검증하기 전에는 지상 주행을 진행하지 않는다.

## 수치와 보고서 해석

이동 및 모터 화면은 알고리즘 요청·안전 속도·실제 송신·수신 명령·휠 목표와 측정값을 구분한다. 실제 장치 모드에서는 카메라 요청이 모터에 전달되지 않으며, 수동 명령은 모터 동작 시험 영역에서 별도로 표시한다. `cmd_vx/cmd_vy/cmd_w`는 ESP32가 보고한 희망 명령으로, 제한 이후 실제 본체 속도로 단정하지 않는다. 펌웨어에 없는 값은 미보고로 표시한다.

휠 목표/측정은 cm/s, RPM은 바퀴 반지름 2.9cm로 환산한다. 수신이 없으면 미수신·미확인/null이다. `LIVE_UDP`는 실제 수신, `MOCK_UDP`는 자동 검사에 사용한 모의 수신이다. 데이터의 출처와 수신 유효성·나이를 함께 확인한다.

- 명령 처리 정황 없음: 송신·세션·seq·상태·속도 원문을 먼저 비교한다. 미관측이 곧 미실행을 뜻하지는 않는다.
- PWM 0·엔코더 변화 없음: 해당 모터의 제어 단계·출력 차단·fault를 확인한다.
- PWM 관측·엔코더 변화 없음: 모터 전원·드라이버·배선·모터·엔코더·정지 마찰을 실측한다. 원인은 가설이며 출력 제한을 자동 해제하지 않는다.
- 기대 부호와 엔코더 불일치: 해당 모터/엔코더 배선과 방향 설정을 확인한다. 근거 없이 핀·CPR·PID·방향을 바꾸지 않는다.

**진단 보고서 저장 (JSON·Markdown)**은 실행별 `logs/<시각>/diagnosis_*.json` 및 `.md`를 만든다. 실패 단계·네트워크·실행 모드·출처·송수신·fault·최근 시험·모터별 관측·추가 실물 확인 사항을 포함한다. 원문 JSON 필드는 유지하고 Wi-Fi 자격 증명 필드는 기록 대상에서 제외한다. `events.jsonl`의 `UDP_TX`/`UDP_RX`에는 실제 시각·실행 내 단조 시각·주소·명령·소켓 성공/오류·검증 사유를 기록한다. 송신 간격과 이동 워치독을 비교할 수 있다.

보고서는 가장 최근 시험의 요약과 현재 수신값을 포함한다. 시험 전체의 수신 샘플과 이전 시험은 같은 실행 폴더의 JSONL을 함께 공유한다. 자동 검사의 정상 결과, 사용자가 기록한 육안 관찰, 실제 하드웨어 검증은 구분한다.

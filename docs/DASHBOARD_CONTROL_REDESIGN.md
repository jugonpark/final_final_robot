# D.I.G. 중앙 대시보드 개편

## 대시보드 사용 흐름

프로젝트 폴더의 `run_simulation.bat`를 실행하면 시뮬레이션 상태로 열립니다. 상단에서 현재 제어 모드를 확인하고, 그 옆의 **긴급 정지**를 모든 탭에서 사용할 수 있습니다.

| 탭 | 작동 방식 |
| --- | --- |
| 직접 제어 | ESP32 주소를 입력하고, 바퀴를 공중에 고정한 뒤 실물 직접 제어를 한 번 활성화합니다. 새 STOP과 바퀴 상태가 확인되면 방향 버튼과 M1·M2·M3 시험 버튼이 열립니다. 누르는 동안 속도 명령을 보내고, 버튼 해제·탭 이동·창 비활성화에서 STOP을 보냅니다. 이후 새 STOP 응답을 확인한 다음 같은 세션에서 다른 버튼을 누를 수 있습니다. |
| 손동작 제어 | 카메라와 MediaPipe 랜드마크를 표시합니다. 손동작 직접 구동은 사람을 선택하지 않아도 됩니다. 최초 정지 응답 이후 손을 내리거나 주먹을 쥐어 준비합니다. 기본 매핑은 손바닥 전진, 엄지 위 좌이동, 엄지 아래 우이동, 주먹 정지입니다. 방향, 최소 신뢰도(기본 0.70), 연속 프레임(기본 2개), 유지시간(기본 0.25초)은 활성화 전에 조정합니다. 주먹은 즉시 정지로 고정합니다. |
| 손동작 제어 → 사람 추종 | 추종 대상을 선택하고 확정합니다. 실물 추종은 한 번 활성화하면 첫 STOP과 중립 동작 이후 준비됩니다. 기존 손바닥 재개, 주먹 정지, 엄지 위·아래 추종 거리 조정과 시뮬레이션을 유지합니다. 카메라 갱신 실패나 대상 상실 시 추종을 멈춥니다. |
| 자연어 제어 | 기존 Nemotron 어댑터, 스키마 검증, 입력 원문 대조로 계획을 만듭니다. 첫 실물 실행에서 한 번 승인한 뒤 각 계획을 화면에서 확인하고 실행합니다. 같은 주소와 모드에서 연속 시험할 때 이전 승인을 사용합니다. 각 실행의 UDP 세션은 새 STOP·heartbeat로 동기화합니다. 장치 오류, 실행 실패, 긴급정지 또는 제어권 해제 시 승인이 만료됩니다. |
| 진단 | 송수신 세션, 부팅 ID, 순서 번호, 일치 텔레메트리 지연, STOP 결과, 바퀴 상태, 카메라와 추론 지표를 표시합니다. JSONL 경로와 진단 보고서 저장은 기존 기록 기능을 사용합니다. |

바퀴 시험은 기존 ESP32 `cmd_vel`의 저속 모드와 PID를 사용합니다. M1·M2·M3는 각 바퀴에 목표 속도를 줄 수 있도록 기존 3륜 변환식의 역을 사용합니다. 목표 평형 상태에서 선택한 바퀴만 최대 2.5 cm/s를 목표로 합니다. 바퀴는 공중에 고정해서 확인해야 하며, 펌웨어의 가속 제한으로 전환 순간에 다른 바퀴도 움직일 수 있습니다. RPM은 바퀴 반경 2.9 cm를 적용해 텔레메트리 속도에서 환산합니다.

## 송신권과 STOP

동시에 한 모드만 중앙 제어권을 가져갑니다. 해제를 누르면 기존 송신기에서 STOP을 먼저 요청하고, 정지 응답 확인과 소켓 종료까지 다른 모드의 연결을 차단합니다. 응답을 기다리는 동안 대시보드는 계속 갱신됩니다. 정지 응답을 확인할 수 없으면 화면과 로그에서 미확인 상태를 표시하고 구동 모드 전환을 막습니다. 같은 주소에 통신 전용으로 재연결하여 정지 상태를 확인할 수 있습니다.

직접 제어는 GUI가 갱신되지 않거나 통신이 유효하지 않으면 STOP으로 전환합니다. 기본 송신 주기는 100 ms, GUI 갱신 허용시간은 250 ms입니다. 손동작 직접 구동은 새 프레임에서 한 손이 같은 동작을 반복할 때만 움직입니다. 인식 불가, 낮은 신뢰도, 여러 손, 손 소실에서 STOP을 요청하고, 손동작이 다시 인식되어도 새 STOP 응답 전까지 이동을 막습니다. 카메라·통신 장애로 해제된 제어권은 자동으로 되살리지 않습니다. 물리 정지 지연은 실물 측정이 남아 있습니다.

자연어 실행에 오류가 나면 기존과 같이 계획을 중단하고 STOP을 재전송합니다. 새 STOP 순서 번호가 같은 ESP32 주소·포트, 세션, 부팅에서 확인되고, 텔레메트리 시각이 전진하며 명령·PWM이 0, 바퀴 보고 속도 절댓값이 0.3 cm/s 미만일 때 출력 정지로 기록합니다. Fault가 래치된 경우도 이 경로에서 출력 정지만 확인합니다. 오류는 해제하지 않으며 실패한 계획의 후속 이동도 실행하지 않습니다.

## ENCODER_JUMP 조사

`logs/llm/9146636137ca4f168d2e2b0ee325a7a7.jsonl`에서 2026-11-17 19:43:55.722 KST에 `DISTANCE_ACTIVE`가 관측됐습니다. 세션은 4255845985, 부팅 ID는 3557285028, 순서 번호는 8이었습니다. 엔코더 누적 카운트는 `[134,-283,131]`, PWM은 `[0,-47,49]`, 바퀴 보고 속도는 약 `[0,-6.85,5.50]` cm/s였습니다. 19:43:55.911에 동일 세션·부팅에서 순서 번호 9의 `ENCODER_JUMP`가 들어왔습니다. 이후 STOP 11–13의 소켓 송신은 기록됐고, 당시 Python 검증기는 Fault 응답을 받으면 STOP 확인을 종료했습니다. 이 로그로 물리 정지 여부는 확인할 수 없습니다.

펌웨어의 x1 엔코더는 A 채널 상승 에지에서 B 채널을 읽습니다. 소스 기준 GPIO A는 34·16·32, B는 35·17·33입니다. 설정은 898 counts/rev, 반경 2.9 cm, 바퀴 속도 한도 20 cm/s, 점프 여유 계수 3입니다. 정상 10 ms 제어 주기에서 허용 변화량은 약 30 카운트입니다. 200 ms 텔레메트리에는 오류 바퀴와 제어 틱별 변화량이 없습니다. 갑작스러운 변화는 감지됐지만 배선, 펄스 노이즈, CPR 불일치, 방향 또는 타이밍 중 어떤 것이 원인인지는 결정할 수 없습니다. PID, GPIO, CPR, 임계값 및 펌웨어는 수정하지 않았습니다.

승인 후 먼저 무구동 상태에서 전원, 공통 GND, A/B 채널 및 풀업을 확인합니다. 바퀴를 손으로 한 바퀴씩 돌려 순 카운트 절댓값이 설정과 일치하고 카운트 방향이 반복 가능하며 정지 중 카운터가 유지되는지 확인합니다. 이어 바퀴를 공중에 고정한 저속 시험에서 각 바퀴의 목표·실측 RPM, PWM, 카운트 변화와 STOP 지연을 기록합니다. Fault가 재현되면 틱별 `dt`, 세 바퀴의 `deltaCount`, 해당 틱의 임계값과 A/B 신호를 확보한 뒤 임계값 보정 여부를 판단합니다. 이번 작업에서 실물 주행과 펌웨어 업로드는 수행하지 않았습니다.

## 카메라 측정

이전 카메라 JSONL `logs/20261117_194242_990802/events.jsonl`의 고유 처리 프레임 5,073개에서 캡처부터 인식 완료까지 P50 188.8 ms, P95 261.3 ms였습니다. 같은 로그에서 `CAMERA_FAILED_OR_STALE` 상태 기록이 262회 나왔습니다. 한 상태가 여러 번 기록될 수 있습니다. 이전 로그에는 YOLO와 MediaPipe의 개별 시간 및 큐 지연이 없어 과거 추종 중단의 정확한 단계는 확정할 수 없습니다.

이제 캡처 호출 시간, 인식 이전의 대기 시간, YOLO와 MediaPipe 소요시간, 캡처 및 처리 FPS, 결과가 사용될 때의 영상 나이와 최신 프레임 슬롯에서 건너뛴 누적 프레임을 기록합니다. 직접 손동작 모드에서 YOLO를 건너뜁니다. 기존 최신 프레임 한 슬롯 방식을 유지합니다. UDP 이동 로그에서 인식 완료 시각·영상 시각·송신 시각으로 명령 전달 지연을 계산할 수 있습니다.

합성 프레임 30개를 실제 MediaPipe 모델로 처리했을 때 손동작 전용 경로에서 큐 대기 P50/P95 5.56/14.71 ms, MediaPipe 20.89/26.87 ms, 프레임 생성부터 처리 완료까지 26.87/32.31 ms였습니다. 실제 카메라 장치는 이 세션의 실행 환경에서 열리지 않았습니다. 손 랜드마크의 현장 정확도, 카메라의 실제 FPS, YOLO 단계별 실제 지연, 인식부터 실물 응답까지의 지연은 미검증입니다.

### 11월 18일 실제 카메라 재확인

Windows 세션에서 MSMF로 640×480 카메라 프레임 20장을 1.12초에 읽었습니다. 이전 대시보드 실행은 카메라 수신 상태에서 첫 인식 결과를 기다리느라 영상 영역이 비어 있었습니다. 합성 입력 진단에서 첫 추론 중 PyTorch·TorchVision 초기 로딩을 관측했습니다. 새 화면은 인식이 준비될 때까지 최신 원본 프레임을 표시하고, 원본 영상만 표시되는 동안에는 제어용 인식 데이터를 생성하지 않습니다.

실제 카메라를 연결한 시뮬레이션 검증에서 원본 영상은 2.35초에 표시됐고, 연속된 YOLO·MediaPipe 처리 결과는 20.55초에 확인했습니다. 회귀 테스트는 최초 원본 영상 표시와 오래된 프레임 제거를 포함해 격리 사본에서 130개 통과했습니다.

## 검증 및 기록

- 회귀 기준은 기존 123개입니다. 승인된 UDP 실물 실행 없이 소프트웨어 테스트를 실행했습니다. 이 체크아웃의 로컬 `secrets.h` 때문에 원래부터 배포본 검사 1개가 실패합니다. 로컬 자격 증명 파일을 그대로 두고, 이를 제외한 격리 사본에서 원본 ZIP 해시와 펌웨어를 포함한 전체 129개 테스트를 통과했습니다.
- 추가 테스트로 바퀴별 역변환, 반복 프레임과 잘못된 손동작 차단, 손 소실·카메라 장애 STOP, 비동기 제어권 해제, 엔코더 오류 후 동일 세션 STOP 확인, 자연어 세션 재승인을 확인했습니다. 기존 GUI 테스트를 네 탭 및 누름·해제 입력 흐름에 맞췄습니다.
- PySide6 네 탭을 960×700과 1320×920의 합성 미리보기로 렌더링했습니다. 대시보드 NLP 경로는 모의 Nemotron·ESP32로 확인했습니다. 이번에는 실제 NVIDIA 연결을 새로 호출하지 않았습니다.
- 실물 시험 로그에는 시각, 제어 모드, TX/RX 세션, 부팅 ID, 송신·수신 순서 번호, 동작과 목표 거리, 실측 거리 및 오차, 바퀴별 목표·실측 RPM/PWM/카운트, heartbeat 간격, STOP 요청·응답·실제 정지 시각, Fault 및 운영자 관찰을 남깁니다. 물리 거리와 실측 정지 시각은 관찰값을 별도 기록합니다.

# RAG 답변 사용성 복구 계획

2026-11-26. 코드와 현재 작업환경 설정을 읽고 작성한 계획이다. 운영 코드·클라우드 설정을 바꾸지 않았으며 새 외부 API 요청도 하지 않았다.

## 진단

1. **홍승조 답변은 생성 모델의 문제가 아니다.** `knowledge/facts.py`는 소개의 각 필드를 `사용자가 제공한 소개에서 {이름}의 {필드}: {값}.`으로 만든다. `rendering.py`는 그 문자열을 빈 줄로 연결하고, `validate_final`은 같은 결과만 허용한다. 검증용 사실 단위와 사용자에게 읽힐 문장 단위를 동일하게 취급한 설계가 반복을 강제한다.
2. **프로그램 설명의 보류는 곧 의미 검증 실패라는 뜻이 아니다.** 현재 작업환경의 `load_environment()`에서 `DIG_KNOWLEDGE_CLOUD`는 미설정이다. `cloud_allowed`는 명시적인 `1`만 허용한다. 이 설정이면 자유 생성 단계 자체를 건너뛴다. 반면 로컬 템플릿은 소개·전압·핀·BOM 등만 지원하고 프로그램 개요는 지원하지 않는다. 결과적으로 문서가 있어도 개요를 답할 경로가 없다.
3. **보류 메시지가 원인을 숨긴다.** 정책상 미실행, 근거 부족, 생성 오류, 결정론적 오탐, 의미 검증 실패가 거의 같은 문구로 보인다. 이번 해당 답변의 실행 메타데이터 조회는 로컬 HTTP 10초 시간 초과로 실패했다. 당시 원인을 직접 확인한 것으로 기록하지 않는다.
4. **Phase 2.6은 아직 웹에 연결되지 않았다.** 현재 사용 중인 웹은 기준선이다. 후보의 59개 로컬 검사 통과를 사용자가 보는 답변 품질 개선으로 바꿔 설명하면 안 된다.
5. **후보도 개요 문제를 다 풀지 못했다.** 통신/UI/UNKNOWN 중심의 facet과 키워드 관련성 검사로는 넓은 소개 질문을 충분히 처리하지 못한다. 참인 짧은 결론도 키워드 수 때문에 탈락할 수 있다. 접속어/문장 수 기반 복합 주장 검사는 의미적으로 하나인 자연스러운 관계 설명도 과하게 막을 수 있다.
6. **문서의 버전 문제도 남는다.** 과거 Qt 기본 UI 설명과 현재 HTML/Python 웹 관제 설명을 구분해야 한다. 같은 Git 리비전에 존재한다는 사실만으로 모든 문장이 현재 운영 설명이 되지 않는다. 현재 구현·과거 구조·계획을 구분해 검색해야 한다.

## 해결 원칙

- 검증 규칙을 일괄 완화하지 않는다. 근거가 충분하고 표현만 어색한 경우, 기능이 정책상 꺼진 경우, 실제 의미가 미확인인 경우를 구분한다.
- 내부의 원자적 사실과 화면/음성의 문장 구조를 분리한다. 각 표현이 어떤 검증된 사실을 담는지 역추적할 수 있어야 한다.
- 사용자 소개의 출처 한정은 한 번 표시하되, 별명·농담을 공식 경력으로 확대하지 않는다. 부정·조건·수치·시점 한정은 문장 결합 후에도 유지한다.
- 기본 개요를 외부 모델에 전적으로 의존시키지 않는다. 승인 없는 클라우드 활성화나 사용자 문서 전송으로 문제를 우회하지 않는다.
- 의미 검증 전 자유 생성문을 보여 주거나 TTS로 내보내지 않는다. 검증되지 않은 설명을 재서술로 세탁하지 않는다.

## 구현 순서

### 1. 원인 관측부터 분리

모델 미실행/정책 차단/근거 부족/생성 실패/인용 실패/규칙 실패/의미 판정별 내부 reason code를 만든다. 원문이나 비밀정보를 운영 로그에 남기지 않는다. 보류율을 하나로 합치지 않고 단계별로 센다. 화면에는 필요한 경우만 짧게 이유를 안내한다.

완료 기준: cloud=0에서 모델을 부르지 않고 `POLICY_DISABLED`로 구분한다. 잘못된 인용과 의미 모순도 서로 다른 코드로 남는다. 동일한 문구만 보고 원인을 추정하는 상태를 끝낸다.

### 2. 사용자 소개의 로컬 표현 개선

기존 MD 필드 파서와 출처 연결을 유지한다. 소개 필드/값을 중간 구조로 보존하고, 인물 소개용 결정론적 renderer에서 조사·종결어미와 나열을 처리한다. 출처 한정은 소개 앞에 한 번만 둔다. 임의 LLM 재서술은 필요하지 않다.

표현 목표 예시(새 실제 출력이 아님):

> 적어주신 소개에 따르면, 홍승조의 직업은 ‘뮤즈 장로드래곤’, 전공은 ‘20학번 전전’이에요. 역할은 ‘넘어지기’이고, 자칭 삼성팬이며 브리또·원피스 옷·포켓몬을 좋아한다고 해요. 여기서 원피스는 애니메이션이 아니라 옷을 뜻해요.

실제 구현에서는 `자칭 삼성팬`을 별도의 실제 팬 활동 경력 등으로 확장하지 않고 원래 필드 값으로 유지한다. 결합 문장에 원래 없던 사실·평가·원인 관계를 만들지 않는다. 임의 인물명에도 작동하게 하며 홍승조 전용 문자열을 넣지 않는다.

완료 기준: 한 번의 출처 한정, 반복 없는 연결된 문장, 네 필드와 ‘애니 아님’ 보존, 값 변조/누락 차단, speech_text와 동일한 사실, 출처 클릭 유지. 기존 literal reply 일치 검사 대신 이 renderer의 입력 사실과 최종 문자열 계약을 검사한다.

### 3. 프로그램 개요의 로컬 근거 경로 추가

프로그램의 목적·주요 기능·실행 UI/백엔드·장치 통신 역할을 문서의 명시적 구조화 사실로 정리한다. 기존 MD 기반 지식 관리에 맞추고 각 항목에 근거 경로·리비전·원문·시점·구현/계획 상태를 붙인다. 사람이 검토하지 않은 자료를 승인 완료로 표시하지 않는다.

질문은 개요/기능/구조/통신/사용 방법으로 범위를 나눈다. 개요 질문에는 필수 2~4개 사실을 우선하고 세부 포트·파일·설치 경로는 생략한다. 단일 정답 문장을 질문별로 하드코딩하지 않고, 질문 범위에 맞는 동일 사실 자료를 조합한다. Web과 Qt의 관계를 자료의 적용 시점에 맞게 설명한다.

명시적 필드의 결정론적 조회·표현과 자유로운 의미 해석을 구분한다. 로컬 필드 조합 결과를 실제 LLM semantic verification 완료로 표시하지 않는다. 새 문서 초안이 검토/고정되기 전에는 근거를 꾸며 개요를 내보내지 않는다. 출처가 철회되거나 충돌하면 해당 항목만 보류한다.

완료 기준: cloud=0에서도 확정된 개요 자료로 짧은 소개를 제공한다. ‘우리 프로그램 설명’, ‘이 시스템은 뭘 하는 거야?’, ‘어떤 기능이 있어?’ 등 표현이 달라도 맞는 범위를 선택한다. 현재 장치 상태나 하드웨어 성능을 설명에 끼워 넣지 않는다.

### 4. 복잡한 설명은 생성 단계에서 자연스럽게 작성

개요 밖 해석이 필요한 질문은 Phase 2.6 후보의 검색/ID 구조를 재사용한다. ‘하나의 주장’은 **하나의 검증 가능한 관계**로 정의한다. 주어·대상·프로토콜을 포함하는 하나의 관계까지 무조건 여러 문장으로 쪼개지 않는다. 독립 사실을 무관하게 묶은 경우만 분리/거절하도록 정상·반례로 보정한다.

자연스러운 존댓말과 설명 순서는 검증 전 최초 생성에서 확보한다. 검증 후 renderer는 승인된 문장과 출처 한정만 배치한다. 별도 자유 재서술 호출은 기본적으로 추가하지 않는다.

의미 검증은 실제 지지 근거를 사용하며 수치 대상/단위/부정/조건/버전/설계 상태를 유지한다. 키워드 수 검사만으로 옳은 짧은 결론을 최종 거절하지 않도록 개요/관계별 필수 요소와 근거 연결을 검사한다. 이 역시 보정된 의미 점수로 과장하지 않는다.

완료 기준: 결론이 먼저 나오고, 직접 답하는 사실이 남는다. 선택적 세부 사항이 탈락했다는 이유로 핵심까지 전체 보류하지 않는다. 핵심 사실이 없을 때는 주변 설명만으로 답변을 완성하지 않는다.

### 5. 사용 가능한 범위에서 답하고 부족한 부분만 한정

판단을 ‘통과 claim 존재 여부’가 아니라 ‘질문에 필요한 핵심 사실이 지지되는가’로 바꾼다. 선택 정보 누락과 필수 정보 누락을 구분한다. 필수 일부가 확인되면 그 부분을 먼저 설명하고 부족한 항목만 안내한다. 완전히 다른 주제의 참인 claim은 답변 근거로 세지 않는다.

정책상 외부 설명이 꺼졌다면 사실 오류처럼 안내하지 않는다. 로컬 확인 내용이 없을 때만 구체적인 확인 질문을 한다. 일반 개요처럼 답할 수 있는 질문에서 사용자가 반드시 기술 용어를 더 입력하게 만들지 않는다.

## 검증과 채택 기준

먼저 소개/개요/관계 설명/수치/부정/조건/계획/실시간/개인정보 질문을 분리해 로컬 검사한다. 기존 20문항은 provisional을 유지하고, 소개 및 넓은 개요의 새로운 패러프레이즈도 별도 검토한다. 실제 답변을 읽고 핵심 사실 충족, 사실 보존, 불필요한 보류, 반복, 음성 가독성을 독립적으로 주석한다.

평가 지표는 핵심 사실 충족률, 실제 오답 차단, False Rejection, 답변 보류 원인, 반복 표현, 자연스러움을 함께 본다. 검색 표지 포함/Mock ENTAILMENT/테스트 개수로 실제 답변 품질을 대체하지 않는다. 새 임계값을 근거 없이 공식으로 정하지 않는다.

소개 renderer와 로컬 개요 경로는 외부 API 없이 검증할 수 있다. 복잡한 자유 생성 설명의 실제 개선은 별도 승인된 진단 예산 안에서 확인해야 한다. 기존 12/12 장부와 미승인 최대 6회 계획은 그대로다.

채택은 로컬 표현 개선 → 로컬 개요 경로 → 실제 평가를 마친 자유 생성 후보 순서로 나눈다. 모든 RAG를 한 번에 갈아끼우지 않는다. 현재 서버 재시작·클라우드 활성화·Phase 2.6 운영 연결·커밋/푸시는 이번 계획 작성에 포함하지 않는다. 안전/개인정보/미션 승인 정책도 유지한다.

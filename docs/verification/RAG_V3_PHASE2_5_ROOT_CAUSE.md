# D.I.G. Phase 2.5 — RAG Quality Recovery & Evaluation Calibration

작성일: 2026-11-26 (Asia/Seoul). 브랜치 `codex/grounded-rag-v3`. 기존 미커밋 변경을 보존한 로컬 분석이다. **이번 외부 API 요청은 0회**이며 기존 12/12 장부는 그대로다.

## 핵심 결론

세 사례의 불완전한 답변을 “의미 검증 모델이 너무 엄격해서”라고만 설명할 수 없다. 원시 생성 블록은 11개였고 **9개가 의미 검증 이전에 제외**됐다. 남은 2개는 당시 실제 judge가 모두 ENTAILMENT로 판정했다. 주요 원인은 질문의 핵심 근거 선택 누락, 복수 사실을 한 블록에 묶은 생성과 잘못된 인용 번호, 그리고 문단 전체의 단어를 조건으로 해석한 결정론적 오탐이다.

원문을 확인한 정답 초안 20문항을 **53개의 독립 사실**로 다시 구성했다. 인간 검토 완료로 표시하지 않았고, 시험 후보가 기존 평가와 의미상 중복될 수 있다는 사실도 남겼다. 이번 결과는 개선 후보와 실패 원인을 확인하는 근거이며 실제 품질·지연 개선의 증명은 아니다.

## 1. 061 — 노트북과 로봇의 통신

| 항목 | 원문 대조 결과 |
|---|---|
| 질문 | 우리 프로그램은 노트북이랑 로봇이 어떻게 통신해? |
| 핵심 의도 | UDP 통신과 명령/텔레메트리의 방향. 카메라 처리 순서는 부가 정보 |
| 확인 가능한 정답 | 문서의 PC 통신은 UDP. ESP32 명령 전달과 PC 텔레메트리 수신 경로가 있다. 포트 8888/8889는 선택적 상세 |
| 검색된 근거 | ARCHITECTURE 5개 청크와 대화 예시 1개. 통신 표/정확한 명령·텔레메트리 설명은 선택되지 않음 |
| 생성 | 3개 블록: 통신+파일 소유권 / 기본 시뮬레이션+기존 펌웨어 재사용 / 카메라→GUI 처리와 GUI I/O 분리 |
| 차단 | c1 ENTITY_MISMATCH, c2 DESIGN_QUALIFIER_DROPPED |
| 의미 검증 | c3만 실제 judge에 전달됐고 ENTAILMENT |
| 최종 | 카메라→GUI 처리 순서와 나머지 보류 안내 |
| 누락 | UDP 및 명령/텔레메트리 방향이라는 핵심 답변 |

**c1은 전역 문서에 맞는 사실이 섞였더라도, 고른 인용만으로 전체 주장이 성립하지 않는다.** 선택 인용은 `communication/esp32_udp.py`의 소켓 소유권 등 파일 책임을 설명한다. 이 한 인용을 PC/ESP32/UDP 통신 전체의 증거로 쓰면서 여러 사실을 한 문장에 묶은 것이 문제다. c1 전체 거절을 단순 False Rejection으로 세지 않는다.

**c2는 확인 가능한 규칙 오탐이다.** 근거의 “목표 손 제스처”에서 `목표`가 DESIGN 정규식에 일치했다. 목표 인물/손동작의 target과 향후 설계 목표를 구분하지 못했다. ESP32 운동학·PID·엔코더·워치독 재사용과 Python 상위 제어 추가는 같은 근거에 직접 적혀 있다. Phase 2 개발 후보에서 이 블록이 추가 통과한 실제 기록(1→2)이 있지만, 그 기록이 이번 새 후보 전체의 실모델 검증을 대신하지는 않는다.

c3은 당시 검증된 내용이지만 질문의 핵심이 아니다. renderer가 통과 문장만 그대로 조립하므로 핵심 c1이 사라지면 주변 설명이 답변 전체가 된다. “문서에 맞는 문장”과 “질문에 충분히 답한 문장”은 별도로 평가해야 한다.

## 2. 062 — Qt 사용 기술

| 항목 | 원문 대조 결과 |
|---|---|
| 질문 | Qt 화면은 어떤 기술로 만든 거야? |
| 핵심 정답 | ARCHITECTURE의 “배치 실행의 기본 UI는 PySide6” |
| 검색 | 대화 예시·파일 변경·현재 LLM 동작·실행 안내 등. **전달된 6개 body/인용 후보에는 PySide6가 없음** |
| 생성 | PyQt/PySide+4탭 / 실행 파일+runtime / 일반 LLM 스트림과 Qt 표시 / 실행·설치 방법 |
| 차단 | ENTITY_MISMATCH / CONDITION_DROPPED / CONDITION_DROPPED / SOURCE_TEXT_IN_REPLY |
| 의미 검증 | 호출하지 않음. 4개 모두 전단에서 제외 |
| 최종 | 직접 근거와 설명을 검증하지 못했다는 보류 |
| 누락 | 실제 Python 바인딩 PySide6 |

- c1의 PyQt/PySide는 정확한 바인딩 근거가 없는 생성이다. 4탭 정보도 선택한 인용 후보와 다른 후보에 있었다. 이를 통과시키도록 entity 규칙을 없애면 안 된다.
- c2는 인용의 **`latest-only worker`에서 `only\b`가 일치**해 전역적인 조건 누락으로 처리됐다. 경로·모듈 역할의 사실과 latest-only 속성은 분리해서 평가할 필요가 있다. 이 블록은 실행 파일과 runtime이라는 여러 사실을 함께 담고 있고 음성 답변에 불필요한 파일 경로도 포함한다.
- c3의 조건 일치에는 “검색 문서 발췌는 대화 생성 문맥에서 **제외**” 같은 다른 설명이 포함됐다. Qt가 누적 텍스트를 화면 주기에 표시한다는 부분은 직접 근거가 있다. 다만 생성문이 일반 대화 스트림을 전체 LLM 응답으로 일반화했을 가능성도 있어 블록 전체를 확정 정답으로 보지 않는다. **정상 부분+범위 누락 가능성이 섞인 복합 블록**으로 분류했다.
- c4의 `requirements.txt`는 SOURCE_TEXT_IN_REPLY 규칙에 정상적으로 걸렸다. 설치 방법은 질문의 핵심도 아니다. 현재 `.py` 등 모든 확장자가 동일하게 차단되는 것은 아니므로 음성 출력 검토에는 별도 보완이 필요하다.

즉 올바른 바인딩 원문이 저장소에 있어도 검색/근거 선택에서 빠지면, 생성기가 배경 지식으로 빈자리를 채우고 검증기는 답변 전체를 보류할 수 있다. 이 질문은 judge 모델 교체만으로 해결되지 않는다.

## 3. 063 — 레이더 UNKNOWN

| 항목 | 원문 대조 결과 |
|---|---|
| 질문 | 레이더가 UNKNOWN이면 무슨 뜻이야? |
| 핵심 정답 | 값 미수신/검증 불가 표시. RADAR_NO_DATA와 RADAR_SENSOR_UNKNOWN처럼 구체 사유를 구분해야 함 |
| 생성 | UNKNOWN 의미 / CLEAR 차단 해제 조건 / 미연결·1차 시뮬레이션 UNKNOWN / RADAR_TIMEOUT과 상태 유지 |
| 차단 | c1·c2·c4의 quote_index가 실제 후보 범위 밖 |
| 의미 검증 | 유효 인용을 가진 c3만 전달, 당시 ENTAILMENT |
| 최종 | 미연결·관측 없음과 시뮬레이션 UNKNOWN 설명, 나머지 보류 |
| 누락 | 단순 미연결 외의 센서 유효성·수신 사유 구분 |

범위 밖 인용 3건은 정상 차단이다. 원문에 비슷한 문장이 있다는 이유만으로 서버가 잘못된 번호를 임의로 승인하거나 다른 인용으로 바꾸면 안 된다. 같은 문장을 재사용하더라도 올바른 인용과 의미 검증을 다시 확보해야 한다.

통과한 c3의 문서 전체는 실제 설명과 맞지만 전달된 legacy 청크는 `UNKNOWN을`에서 끝난다. 의미 검증기가 이를 ENTAILMENT로 판정했다는 사실과 근거가 완결된 문장이라는 사실은 다르다. legacy 청킹의 잘림 경고 부재/근거 선택 완결성도 확인해야 한다. 새 생성 성능이나 E5 운용 경로의 실패율로 확대 해석하지 않는다.

## 4. Gold 오류와 실제 답변 오류의 분리

| 평가 데이터 문제 | 실제 파이프라인 문제 |
|---|---|
| 061은 UDP 표가 prose-card 필터에서 제외되면서 무관한 provenance 문단이 정답으로 선택됨 | 실제 검색 결과에도 통신 표가 없고, 생성이 파일 책임 인용에 여러 통신 사실을 연결 |
| 062의 설치 설명은 바인딩 정답을 완전하게 제공하지 않음 | 실제 검색 근거에서 PySide6가 누락되고 생성은 PyQt/PySide를 제시 |
| 문단 하나를 required fact 하나로 취급해 사실별 Coverage 계산이 불가능 | 실제 생성도 복수 사실을 한 claim에 묶어 일부 오류로 정상 부분까지 소실 |
| 120개는 provisional, 180쌍은 템플릿형·인간 미검토 | 30/30 기존 NLI 일치가 실제 복잡한 주장·인용 연결의 정확도를 입증하지 않음 |

새 core20은 잘못된 정답 문단을 재활용하지 않았다. 원문에서 **정확히 한 번 매칭되는 명시적 근거**를 지정하고, 매칭이 없거나 모호하면 오류로 중단한다. 자동 fallback으로 다른 문단을 정답으로 넣지 않는다. 다만 원문 대조는 에이전트가 했으며 인간 승인과는 다르다.

## 5. 20문항 검토 설계

단순 사실 4 / 기술 구조 5 / 수치·단위·부품 3 / 버전 비교 2 / 복합 2 / 근거 부족 2 / 현재 상태 혼동 2. 개발 10 / 시험 후보 10이다.

53개 사실은 subject–relation–value와 문서 범위를 가진 독립 문장으로 작성했다. 동일한 긴 인용이 여러 사실을 뒷받침할 수 있지만 정답 단위 자체를 문단으로 계산하지 않는다. 포트·파일 위치처럼 질문 핵심에 필수적이지 않은 상세는 선택으로 분리했다. 근거 부족/실시간 질문은 임의 실측값을 채우지 않고 보류 행동과 범위 근거를 따로 기록했다.

061·062·063과 의미가 같은 새 질문은 `confirmed_seen_diagnostic`으로 표시했다. 나머지 질문은 기존 120개와의 어휘 유사 후보 ID를 검토 보조로 제시하되, 어휘 유사도를 의미 동일 판정으로 쓰지 않았다. **시험 후보는 아직 pristine holdout이 아니다.** 인간 검토 후 사실 중복과 기존 노출 여부를 확정해야 한다.

별도 의미 중복 검토표에서는 기존 120개 질문을 실제로 읽고 같은 의도·부분 사실·관련 주제를 구분했다. 기존 후보에는 정확히 같은 질문이 반복되고, 같은 질문에 서로 다른 required-fact 후보가 연결된 그룹도 있다. 따라서 데이터 행 120개를 독립적인 120개 사용자 의도로 해석하지 않는다.

Gold의 기준은 커밋 `8861848`의 문서 서술이다. 특히 CENTRAL_CONTROL_WORKFLOW는 변경 전 구조를 보존한 절이 있으므로 전체 엔진 구조나 현재 세션 정책의 정답으로 확대 사용하지 않는다. 통신 경로 인용은 CONTROL_SIMPLE_V2_PLAN의 포트 계약과 함께 한정해서 읽는다. CAD/BOM/펌웨어 자료는 실물 탑재·승인·현재 상태로 승격하지 않는다.

## 6. 결정론적 후보와 반례

운영 `verifier.py`는 변경하지 않았다. [오프라인 후보](../../scripts/rag_phase2_5_candidates.py)의 `None`은 **추후 의미 검증에 보낼 수 있음**을 뜻하며 정답/verified가 아니다.

| 조사 항목 | 재현 | 후보와 유지한 반례 |
|---|---|---|
| 설계/구현 | 목표 손 제스처 때문에 구현 사실이 DESIGN 누락으로 차단 | target과 설계/성능 목표를 구분. CAD metadata·명시 설계 목표→실측 주장은 계속 차단 |
| 수치 대상 | 같은 절에 ESP32 5V와 모터 12V가 있으면 맞는 ESP32 5V도 거부 | 좁은 전압 주어–값 문법의 실제 매칭 구절만 확인. 12V 교환, A 단위 변경, 충돌 값, 조건/부정/설계가 있는 경우는 완화하지 않음 |
| 부정 범위 | Qt 사실과 무관한 모터 미검증 문장이 문단에 있으면 Qt 사실도 거부 | 명시적 다른 주어의 조건만 분리하는 후보. 같은 주어와 다만/해당/그 등 암묵적 연결은 보수적으로 유지 |
| 한국어 부정 누락 | `5V가 아닙니다`의 `아닙`은 기존 `아니`와 다름 | 후보는 아닙/아닌/아님/아닐을 추가. 원 규칙에서 누락돼도 마지막 semantic judge가 거절할 수 있으므로 최종 시스템의 오답 통과를 관측했다고 주장하지 않음 |
| 복수 사실·버전 | 두 대상 전압이나 두 프로파일이 한 claim에 섞임 | 단순히 entity/version/quantity 검사를 삭제하지 않음. 잘못 섞인 값과 버전은 유지 차단 |
| 출력 자연스러움 | 긴 블록·반복 주어·핵심 소실 | 생성 때 원자적 결론 우선. 조립은 승인 문자열의 공백 연결만 허용하고 인과 연결어/새 사실 추가 금지 |

관련 원문 조건이 인접 문장/대명사로 이어질 수 있어 범위 선택 후보도 오판할 수 있다. 현재 예제 밖의 한국어 수치 관계·조건 적용을 해결했다고 주장하지 않는다. 로컬 정상/반례가 통과해도 운영 적용은 추가 실제 평가 전까지 보류한다.

## 7. 단계별 응답 지연

기존 실제 결과만 재사용했다. 시간은 초, 미분리 항목은 미측정이다.

| 사례 | 검색 | 근거 선택 | 생성 wrapper | 결정론적 검증 | 의미 wrapper | 조립 | 전체 | 미분리 잔여 |
|---|---:|---|---:|---|---:|---|---:|---:|
| 061 | 0.011 | 미측정 | 20.530 | 미측정 | 6.951 | 미측정 | 29.138 | 1.646 |
| 062 | 0.883 | 미측정 | 12.742 | 미측정 | 미호출 | 미측정 | 18.195 | 4.570 |
| 063 | 0.208 | 미측정 | 13.178 | 미측정 | 11.088 | 미측정 | 25.762 | 1.288 |

세 사례 모두 생성 wrapper가 가장 큰 측정 구간이며, 063은 의미 wrapper도 거의 같은 규모다. 062는 의미 검증을 호출하지 않았으므로 두 번의 대형 모델 호출이 그 지연의 유일한 원인일 수 없다.

기록된 SDK create 구간은 생성 10.635/6.049/10.191초, 의미 0.996/미호출/0.789초다. wrapper와 create 사이에는 클라이언트 초기화·종료, 직렬화·검사, Python/호스트 스케줄링 등이 들어갈 수 있지만 과거 trace만으로 각각 배분할 수 없다. 잔여를 deterministic 또는 모델 순수 추론 시간으로 임의 배정하지 않는다.

[로컬 SDK 초기화 probe](rag_v3_phase2_5/sdk_local_probe.json)는 dummy key와 막힌 소켓으로 생성/종료만 측정한 새 오프라인 자료다. 과거 실제 요청의 지연 분해로 소급 사용하지 않는다. 모델 생성/검증의 실제 새 latency 및 개선율은 이번에 측정하지 않았다.

이 probe의 3회 관측값은 약 2.562/1.418/1.412초였다. 적어도 클라이언트 준비 비용을 0으로 가정할 수 없다는 단서지만, 당시 wrapper의 모든 미분리 비용을 SSL/연결 초기화로 확정하는 증거는 아니다. 실제 네트워크·서버 추론 시간을 분리하려면 별도 승인된 trace가 필요하다.

## 8. 자연스러움과 speech_text

061은 생성 시 핵심 설명이 있었지만 잘못된 support로 사라졌고 주변 설명만 남았다. 062는 핵심 바인딩의 검색이 실패한 상태에서 경로·설치·스트리밍을 나열했다. 063은 의미를 설명하는 생성문이 있었지만 잘못된 quote_index 때문에 시뮬레이션 사례만 남았다. 검증 후 renderer가 새 결론을 만들어 채우는 방식은 사용하지 않는다.

프롬프트 후보는 첫 claim의 질문 직접성, 사실 하나당 claim 하나, 정확한 인용 범위, 부가 설명 축소와 선택 정보의 불필요한 unanswered_aspects 제거를 요구한다. 파일명·경로를 음성 본문에 넣지 않고 일반 대화/문서 범위를 보존해야 한다. 기존 speech_text와 운영 renderer는 유지했다. 실제 후보 모델 답변이나 자연도 점수는 없다.

## 9. 경량 검증기 선정 기준

현재 모델보다 작다는 이유만으로 선택하지 않는다. 후속 후보에는 다음을 확인한다.

1. 독립 검토된 한국어 기술 NLI: 정상 패러프레이즈와 수치 대상 교환·단위·부정·예외·CAD/실측·버전 혼합을 균형 있게 평가.
2. 전체 Accuracy보다 False Acceptance/False Rejection, unknown/UNAVAILABLE과 답변 Coverage를 함께 기록.
3. 라이선스·배포 범위·한국어 지원 근거·입력 길이·모델/토크나이저 hash 고정.
4. 현재 PC에서 cold/warm CPU·RSS·P50/P95, 입력 절단과 정규화의 영향 측정. 다른 프로세스에서 로딩하며 제어 루프/STOP은 기존 경로 유지.
5. 외부 검증기에는 동일 개인정보 정책, 로컬 NLI는 명시적 설치만 허용. 실행 중 자동 다운로드나 고장 시 검증 성공 처리는 금지.
6. 범주형 판정에 허구의 confidence를 붙이지 않음. 임계값은 실제 점수가 있을 때 별도 보정.

이번에는 새 모델·라이브러리를 설치하거나 모델 목록/API를 조회하지 않았다.

## 10. 추가 실제 API 계획 — 별도 승인 필요

현재 장부는 **12/12 그대로**, 이번 승인·호출은 **0회**다. 아래는 서로 다른 목적의 후속 계획이며 지금 실행하지 않는다. 기존 장부 초기화·우회로 예산을 만들지 않는다.

| 목적 | 계획 호출 | 검증할 것 | 한계 |
|---|---:|---|---|
| 기존 생성문 기반 규칙 후보만 확인 | 최소 1회 batch judge | 새로 자격을 얻은 문장과 정상/반례를 같은 고정 프로토콜로 판정 | 새 생성문·자연도·실제 end-to-end 개선을 검증하지 못함 |
| 061/062/063의 프롬프트+규칙 복구 확인 | 3 생성 + 3 검증 = 계획 6회 | 같은 원문/범위에서 첫 결론, 올바른 인용, 반례 유지, 필수 fact Coverage, 발화 가독성, 각 단계 시간 | 이미 본 진단 질문이라 일반화/최종 시험 증거는 아님. 중간 차단이면 실제 호출은 더 적을 수 있음 |
| 검토·고정 후 core20 운영 후보 확인 | 보수적 상한 40회 | 질문별 생성/검증 최대 2회; 구조화/현재 상태/보류 경로는 정책상 호출 0회 | 실제 경로별 상한을 사전 확정해야 함. 오염되지 않은 별도 holdout 필요 |

목적이 규칙 진단이면 최소 1회, 질문 단위 응답 복구 확인이면 최소 계획 6회다. 현재 보유 baseline/응답은 재사용하므로 A를 다시 호출할 필요는 없다. 1회와 6회를 무조건 더하지 않는다. 새 모델 metadata 조회가 필요하면 그 요청도 별도 예산에 포함해야 한다.

새 생성 3회 뒤 의미 판정을 하나로 batch하면 4회로 기능 진단은 가능하다. 다만 이것은 현재 질문별 생성+judge 경로의 실제 응답 시간 실험이 아니므로, 질문별 end-to-end 복구를 확인하는 계획에서는 6회를 기준으로 잡는다.

사전 조건: core20 필수/선택 사실과 의미 중복의 독립 검토, 대상 공개 문서/질문의 전송 허용 확인, 고정된 generation/rule 버전과 사례별 허용 ID/번호 목록, raw/실패/단계 시간·실제 토큰 기록. 비공개 문서·질문·파생 요약은 제외한다. 새 승인이 오기 전 실험을 수행하지 않는다.

## 11. Phase 3 전 해결 항목

- 핵심 질문에 필요한 근거가 실제 검색·전달됐는지 확인하는 작은 source-checked 시험을 먼저 통과해야 한다.
- 생성문을 독립 사실로 분해하고 지원 인용을 정확히 연결해야 한다. 잘못된 번호의 자동 승인/자동 의미 추측은 금지한다.
- 규칙 오탐과 부정 누락 후보를 정상/반례·실제 judge로 확인하고, 독립 검토된 정답으로 품질·보류율을 함께 측정해야 한다.
- 음성으로 읽을 때 결론이 먼저 나오고 경로·인용 번호·불필요한 긴 나열이 없어야 한다. 이미 검증된 사실 밖의 재서술은 허용하지 않는다.
- C의 기존 P50 25.76초는 일반 음성 대화 준비 완료로 보기 어렵다. 신규 단계 계측과 연결 비용·생성/검증 예산의 실제 비교가 필요하다.
- 취소·오래된 응답 폐기·STOP·승인 경로와 개인정보 경계는 그대로 유지해야 한다.

## 12. 검증 상태

- `tests/test_rag_phase2_5.py`, `tests/test_knowledge_v3.py`, `tests/test_rag_phase2.py`: **39 passed, 16 subtests passed**. 신규 후보의 정상/반례, core20 근거 및 기존 결과 재현을 포함한다. 실행 로그: [validation.log](rag_v3_phase2_5/validation.log).
- 기존 파일 192개의 SHA-256이 모두 일치하며 변경 파일은 0개다. 기존 요청 장부는 12/12, 이번 외부 요청은 0회다. [보존 확인](rag_v3_phase2_5/preservation_check.json).

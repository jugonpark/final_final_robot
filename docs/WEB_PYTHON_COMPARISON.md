# Python 앱과 HTML 웹 관제 비교

브라우저 단독 중앙관제는 기존 Python 앱의 제어 엔진을 서버에서 실행하고 HTML/CSS/JavaScript로 조작한다. 장치 제어를 JavaScript로 재구현하지 않는다. 에이전트와 챗봇은 기존 웹의 대화·RAG·동작 블록 흐름을 유지한다.

## 실행 방식

| 항목 | Python/Qt 앱 | 브라우저 단독 중앙관제 | 웹 시뮬레이션 | 기존 Qt 공유 웹 |
| --- | --- | --- | --- | --- |
| 실행 | `run_simulation.bat --agent-enabled` | `run_web_control.bat` | `run_web.bat --agent-enabled` | `run_simulation.bat --share-web --web-port 8766 --agent-enabled --open-web` |
| 화면 | PySide6 창 | HTML 브라우저만 | HTML 브라우저 | Qt와 HTML 브라우저 |
| Python 백엔드 | `DashboardEngine` | 동일 엔진 | 동일 엔진, 실물 제어 차단 | Qt 프로세스의 동일 엔진·세션 |
| ESP32 연결 | 운영자 연결 | 웹 설정에서 운영자 연결 | 허용하지 않음 | 웹 또는 Qt 연결 |
| 카메라 | 앱 실행 시 시작 | 상단에서 직접 켜기, 화면 이동 시 유지 | 직접 켜기, 합성 기본, `--web-camera`로 실영상 | Qt 카메라 공유 |
| 실물 승인 | Qt 운영자 확인 | 웹 현재 버전·운영자 확인 | 허용하지 않음 | 웹 또는 Qt 운영자 확인 |
| 종료 | Qt 창 닫기 | 실행 콘솔 Ctrl+C | 실행 콘솔 Ctrl+C | Qt 창 닫기 |

`run_web_control.bat`는 `--ui web --web-control --web-port 8766 --agent-enabled --open-web`을 사용한다. 서버는 이 PC의 `127.0.0.1`에서 실행한다. 포트는 `run_web_control.bat --web-port 8770`, 보드 프로필은 `--hardware-profile PCB_V19`처럼 지정한다. 실행만으로 ESP32 연결, 카메라 촬영 또는 이동을 시작하지 않는다. Agent 대화를 위한 NVIDIA 설정과 선택 의존성은 기존과 같다.

## Python 앱을 기준으로 연결한 기능

| 기능 | HTML에서 사용하는 기존 Python 동작 |
| --- | --- |
| ESP32·레이더 주소 | 주소 검증·로컬 저장, 연결 중 주소 변경 거부 |
| 연결·해제·복구 | 중앙 RobotSession, STOP 확인, 비동기 연결 해제·재동기화 |
| 제어 모드 | 수동·손동작 직접·사람 추종·AI 계획·바퀴 시험, 전환 후 자동 활성화 금지 |
| 수동·바퀴 시험 | 누르는 동안만 유지되는 토큰 입력, 해제·갱신 지연 시 정지, 바퀴 고정 확인 |
| 카메라·대상 선택 | 기존 YOLO/MediaPipe 파이프라인과 최신 프레임 검사, viewer lease, 목표 확인 |
| 손동작·사람 추종 | 기존 매핑·시간 안정화·제어권 및 레이더/STOP 검사 |
| 안전·진단 | 긴급 정지·레이더 재무장, 정지 사유·텔레메트리·추론 지연·시험 상태 표시 |
| 계획 실행 | Python 검증기·실행기·현재 계획 버전·현장 확인, 기존 회전 실행 차단 |

카메라 스트림 공유 여부(`shared_control`)와 제어 기능 제공 여부(`control_available`)를 구분한다. 브라우저 중앙관제는 Qt 카메라를 공유하지 않아도 제어 기능을 제공한다. 제어 기능이 있다는 표시는 장치 연결이나 이동 준비 완료를 뜻하지 않는다.

## 손동작과 AI 계획의 동시 제공

메뉴의 **손동작 직접 제어**와 **AI 이동 계획**은 연결 상태나 현재 제어권과 관계없이 열 수 있다. 화면 이동은 장치 제어 모드나 활성화 명령을 보내지 않는다. 손동작이 실제 이동 제어권을 가진 동안에도 기존 Agent 대화·RAG·계획 생성과 블록 편집을 계속 사용할 수 있다.

물리 이동 제어권은 동시에 하나만 가진다. 상단 **이동 제어권 → 손동작 / AI 계획**은 명시적인 전환 요청이며, Python의 기존 정지·새 STOP 응답 절차를 사용한다. 화면은 현재 제어권과 전환 대상(`pending_mode`)을 구분해 표시하고 응답 대기 중에는 추가 전환과 이동 입력을 막는다. 전환 후에는 자동 활성화하지 않는다. 손동작은 **손동작 제어 활성화**, AI 실행은 검토 요청과 현재 계획 버전의 **실물 실행 승인**이 각각 필요하다. 다른 제어 모드는 기존 설정에서 선택한다.

카메라는 처음에는 꺼져 있다. 어느 화면에서든 상단 **카메라 켜기**로 직접 요청하면 AI 화면을 포함한 앱 내부 화면 이동 후에도 인식과 viewer lease 갱신을 유지한다. 따라서 카메라 보기와 AI 대화는 같은 제어 세션을 사용할 수 있다. **카메라 끄기**, 관제 탭 숨김 또는 닫기 시 해당 보기 lease를 해제한다. 다른 보이는 탭의 카메라 요청이 남아 있다면 Python 카메라를 계속 사용할 수 있다. 다시 보여 영상이 재개돼도 손동작이나 AI 이동을 자동 활성화·승인하지 않는다.

## 웹을 기준으로 유지한 Agent와 챗봇

- 기존 `UnifiedAgent`와 대화 그래프가 LLM의 의도·도구 요청을 처리한다. 상태 조회·화면 이동·제어 모드와 이동 요청은 Python의 허용 도구와 검증을 거친다. 문서 답변 자체가 장치 명령이나 실시간 상태 증거가 되지는 않는다.
- 기존 SSE 대화 스트리밍, 누적 메시지, 대화 삭제와 별도 초안 보존 동작을 유지한다.
- 기존 `DraftStore`의 누적 블록, 자연어 수정, 추가·편집·삭제·순서 변경, 미션 버전 충돌 검사와 실행 검토 요청을 유지한다. 계획 검증 제한과 승인 무효화 조건은 Python이 적용한다.
- RAG는 로컬 FTS5 검색·원문 발췌가 기본이다. 문서 등록, Markdown 절/PDF 쪽, Git 리비전·SHA-256 인용을 유지한다. 선택 벡터 검색은 기존 `DIG_KNOWLEDGE_VECTOR=1` 설정을 따르며 실패하면 FTS5를 사용한다.
- 클라우드 문서 답변은 기존 `DIG_KNOWLEDGE_CLOUD=1` 설정을 따른다. 사용자 업로드 문서와 저장소 밖 문서의 로컬 처리 정책을 유지한다. 상세 조건은 [미션·RAG 안내](DRAFT_MISSION_KNOWLEDGE.md)를 참고한다.
- 2D 경로 미리보기, 실행 타임라인·작업 이력을 유지한다. 경로 미리보기는 실제 위치·방향 측정값이 아니다.

## 브라우저 연결과 정지

브라우저 단독 모드에서는 보이는 관제 탭이 100ms 간격으로 same-origin JSON POST 운영자 확인을 보낸다. GET 상태 조회는 운영자 확인을 대신하지 않는다. 연결 확인 실패 시 화면은 이동·승인 입력을 막고 수동 입력을 해제한다. 수동 입력에는 기존 RobotSession의 더 짧은 운영자 확인 제한(기본 0.25초)과 홀드 입력 제한도 적용된다. 운영자 확인 대화상자는 비동기 HTML dialog를 사용해 확인을 기다리는 동안 연결 감시를 계속한다.

마지막으로 보이는 관제 탭의 확인이 1.5초 동안 없으면 Python이 수동·영상·진행 중인 LLM 실행에 긴급 정지를 요청한다. 여러 탭에서는 다른 보이는 탭이 운영자 확인을 계속 보낼 수 있다. 운영자 확인이 돌아온 뒤 최신 CLEAR가 연속 1초 유지되고 ESP32의 새 STOP·정상 상태가 확인되면 소프트웨어 긴급 정지를 자동 해제한다. 운영자가 없는 동안에는 해제하지 않는다. 이전 수동 홀드·영상 제어 lease·AI 승인은 무효화하며, 새 입력·손동작 활성화·현재 계획의 새 승인이 필요하다.

브라우저 탭을 닫아도 Python 서버는 남는다. 완전히 끝내려면 실행 콘솔에서 **Ctrl+C**를 누른다. 정지 요청이나 모의 테스트의 성공은 실제 모터 정지·정지 거리를 입증하지 않는다.

자동 해제 정책은 Agent 사용 여부와 관계없이 공용 Python 엔진에서 적용한다. 기존 **긴급 정지 확인**과 **레이더 해제 확인**은 명시적 수동 확인 경로로도 남긴다.

레이더 수신 시간 초과는 `fresh=false`, `warning=RADAR_TIMEOUT`, 마지막 상태·경과 시간으로 표시한다. 수신 작업은 계속 유지하며, 이미 해제된 CLEAR의 단순 지연만으로 현재 미션·수동 동작을 취소하거나 새 차단을 만들지 않는다. 이전 위험·UNKNOWN·잘못된 패킷·시작 시 차단은 지연으로 해제되지 않는다. 지연된 CLEAR는 자동 해제에 필요한 연속 1초에 포함하지 않는다.

ESP32 통신 지연은 정상 텔레메트리와 새 STOP이 돌아온 뒤 해제한다. 프로토콜 2의 `ENCODER_JUMP`/`ENCODER_INVALID`는 새 출력 STOP과 정상 엔코더 샘플 10개 이상을 확인한 뒤 기존 `recover()`의 오류 초기화·STOP 재동기화를 한 번 시도한다. 실제 `fault=NONE`, 새 STOP·정상 세션을 관측한 뒤에만 소프트웨어 차단을 해제한다. 기기 재부팅은 기존 STOP 전용 재동기화를 기다린다. 지속되거나 지원하지 않는 Fault, 보드 프로필 불일치, 다른 제어기와의 세션 충돌, Python 감독 오류는 자동으로 무시하지 않는다. 어느 경우에도 예전 이동 패킷·승인을 재사용하지 않는다.

## Qt에 남아 있는 도구와 검증 범위

이번 전환은 일반 관제와 웹 Agent 흐름을 브라우저에서 사용할 수 있게 한다. Qt의 다음 세부 도구는 아직 전용 웹 편집기나 내보내기 화면이 없다.

- 네트워크·수신 포트 probe와 여섯 단계 진단 보고서 JSON/Markdown 내보내기.
- 손동작 인식·추종의 세부 설정 편집기와 엔코더 `STRICT`/`FILTERED_TEST` 정책 변경.
- 레이더 미연결 공중 고정 벤치 승인, 상세 모터 시험 기록·현장 관측 입력과 교정/분석 도구.

웹의 관련 설정은 현재 값 조회와 기존 설정 파일·CLI를 사용한다. Qt 도구를 함께 쓰려면 브라우저 단독 서버를 종료하고 해당 실행 방식으로 시작한다. 두 독립 관제 프로세스로 같은 ESP32나 카메라를 동시에 사용하지 않는다.

소프트웨어 자동 검증에는 모의 장치를 사용한다. 실제 ESP32·레이더·카메라 인식 성능, 모터 동작·물리 정지는 별도 현장 검증 대상이다.
